Languages & Frameworks

Node.js runs JavaScript on the V8 engine with a single-threaded event loop for non-blocking I/O. Mastering its internals is critical for backend roles involving high-concurrency services.

Core Concepts

  • Event Loop Phases: The libuv event loop cycles through phases: timers (setTimeout/setInterval callbacks), pending callbacks (deferred I/O), idle/prepare (internal), poll (retrieve new I/O events), check (setImmediate callbacks), close callbacks (e.g. socket.on('close')).
  • Microtasks vs Macrotasks: Microtasks (Promise.then, queueMicrotask) drain completely between each event loop phase. Macrotasks (setTimeout, setInterval, I/O) execute one per phase iteration. process.nextTick has its own queue that drains before microtasks.
  • process.nextTick vs setImmediate: nextTick fires before I/O and before microtasks; setImmediate fires in the check phase after I/O. Prefer setImmediate for yielding to I/O.
  • Streams & Backpressure: Readable, Writable, Duplex, Transform. pipe() handles backpressure automatically. If writable.write() returns false, pause the readable until the 'drain' event.
  • Clustering vs worker_threads: cluster forks multiple processes sharing a server port (multi-core). worker_threads share memory via SharedArrayBuffer for CPU-intensive tasks within one process.
  • Error Handling: Always handle 'error' events on streams/emitters (uncaught crashes the process). Use process.on('uncaughtException') and 'unhandledRejection' as safety nets, not flow control.
  • CJS vs ESM: CommonJS uses require() / module.exports, synchronous. ESM uses import / export, async, supports top-level await and tree-shaking. ESM is the future standard.

Key Interview Q&A

Q: What happens if you starve the event loop with a CPU-bound task?
The single thread blocks, so no I/O callbacks fire, HTTP requests time out, and the server appears unresponsive. Solutions: offload to worker_threads, break work into chunks with setImmediate, or use a separate microservice for heavy computation.
Q: Explain the order: setTimeout(0), setImmediate, Promise.resolve().then(), process.nextTick()
In the main module: nextTick first (its queue drains before microtasks), then Promise.then (microtask), then setTimeout or setImmediate (their order in the main module is non-deterministic; inside an I/O callback, setImmediate always fires before setTimeout(0)).
Q: How does Node.js handle 10k concurrent connections on a single thread?
Node delegates I/O to the OS kernel (epoll/kqueue/IOCP) via libuv. The event loop just processes callbacks when I/O completes. No thread per connection is needed. The bottleneck is CPU work in callbacks, not connection count.

Python's CPython implementation has unique characteristics like the GIL and reference counting. Understanding these internals helps write performant backend code and answer deep interview questions.

Core Concepts

  • GIL (Global Interpreter Lock): A mutex in CPython that allows only one thread to execute Python bytecode at a time. This means CPU-bound multithreading does not achieve parallelism. Use multiprocessing, concurrent.futures.ProcessPoolExecutor, or C extensions to bypass it. I/O-bound threads still benefit because the GIL is released during I/O operations.
  • asyncio: Single-threaded concurrency via coroutines. async def creates a coroutine; await yields control to the event loop. asyncio.gather() runs tasks concurrently. asyncio.Semaphore limits concurrency. asyncio.create_task() schedules coroutines.
  • Decorators & functools.wraps: A decorator wraps a function. @functools.wraps(fn) preserves the original function's __name__, __doc__, and __module__. Decorators can be stacked; they apply bottom-up.
  • Metaclasses vs __init_subclass__: Metaclasses control class creation (rarely needed). __init_subclass__ (Python 3.6+) is the simpler hook for customizing subclass creation without a metaclass.
  • Generators & yield from: Generators are lazy iterators using yield. yield from delegates to a sub-generator, propagating values and exceptions. Memory-efficient for large datasets.
  • Memory Management: CPython uses reference counting as primary GC plus a cyclic garbage collector for reference cycles. __slots__ replaces __dict__ per instance, reducing memory by ~40% for many small objects.
  • Dunder Methods: __repr__, __str__, __eq__, __hash__, __enter__/__exit__ (context managers), __getattr__/__setattr__, __call__.

Key Interview Q&A

Q: Why can't you use threads for CPU-bound parallelism in Python?
The GIL only allows one thread to execute Python bytecode at a time. For CPU-bound work, threads actually add overhead from context-switching without gaining parallelism. Use multiprocessing (separate processes with their own GIL), or write the hot path in C/Cython/Rust.
Q: What is the difference between asyncio.gather and asyncio.wait?
gather() runs awaitables concurrently and returns results in order; it raises the first exception by default. wait() returns two sets (done, pending) and supports return_when=FIRST_COMPLETED for more flexible control. Use TaskGroup (3.11+) for structured concurrency with proper cancellation.
Q: When would you use __slots__?
When creating millions of instances of a small class (e.g. data records, graph nodes). __slots__ prevents creation of __dict__ per instance, saving ~64 bytes each. Trade-off: no dynamic attribute assignment, and each level of inheritance must redeclare slots.

FastAPI is a modern Python web framework built on Starlette and Pydantic, offering automatic OpenAPI docs, type validation, and async support out of the box.

Core Concepts

  • Pydantic Validation: Request/response models defined as Pydantic BaseModel classes. Automatic validation, serialization, and OpenAPI schema generation. Use Field() for constraints, validator/field_validator for custom logic.
  • Dependency Injection: Depends() for composable dependencies. Common uses: DB session lifecycle (get_db yields a session, ensures cleanup), auth (get_current_user), pagination parameters. Dependencies can be nested and cached per-request.
  • async def vs def: async def endpoints run on the event loop (use for I/O-bound with async drivers). Regular def endpoints run in a threadpool (safe for blocking I/O like sync DB drivers). Mixing blocking code in an async def blocks the entire event loop.
  • BackgroundTasks: Fire-and-forget tasks after the response is sent. Use for sending emails, logging, non-critical side effects. Not a replacement for a task queue (Celery, etc.) for heavy work.
  • Middleware & Lifespan: Middleware wraps every request (timing, CORS, auth). Lifespan events (@asynccontextmanager) replace on_startup/on_shutdown for initializing DB pools, ML models, etc.
  • Router Organization: Use APIRouter for modular route grouping with prefixes and tags. Keep routers thin; business logic in services/repositories.
  • FastAPI vs Django REST Framework: FastAPI: async-first, auto-docs, Pydantic, newer. DRF: mature ecosystem, ORM integration, admin panel, better for monoliths.

Key Interview Q&A

Q: What happens if you call a synchronous ORM inside an async def endpoint?
It blocks the event loop thread, causing all other concurrent requests to stall. Either use def instead of async def (FastAPI auto-runs it in a threadpool), or use an async ORM like SQLAlchemy 2.0 async or Tortoise ORM.
Q: How does FastAPI dependency injection handle cleanup?
Use yield in dependencies: code before yield runs on setup, the yielded value is injected, and code after yield runs on teardown (even if an exception occurs). This is the pattern for DB session management.

Architecture & Design

Microservices decompose a system into independently deployable services organized around business capabilities. Each service owns its data and communicates through well-defined APIs.

Core Concepts

  • Bounded Contexts (DDD): Each microservice aligns to a bounded context — a clear boundary where a particular domain model applies. Services should not share databases.
  • Sync vs Async Communication: Sync: REST (simple, HTTP-based), gRPC (protobuf, streaming, efficient). Async: message queues (SQS, RabbitMQ) for decoupling, event streams (Kafka) for event-driven architectures.
  • Circuit Breaker: Three states: Closed (requests flow normally), Open (requests fail fast after threshold), Half-Open (limited requests to test recovery). Prevents cascading failures.
  • Saga Pattern: Manages distributed transactions. Choreography: each service listens for events and reacts (simple, but harder to trace). Orchestration: a central coordinator directs the saga steps (more control, single point of failure).
  • API Gateway: Single entry point for clients. Handles routing, rate limiting, auth, request aggregation. Examples: Kong, AWS API Gateway, Envoy.
  • Service Discovery: Client-side (service registry like Consul, client picks instance), server-side (load balancer resolves), DNS-based (Kubernetes Services).
  • Strangler Fig: Migrate a monolith incrementally by routing new features to microservices while the monolith still handles legacy paths.
  • Outbox Pattern: Write events to an outbox table in the same DB transaction as the business data. A separate process (Debezium CDC or poller) publishes them to the message broker. Guarantees at-least-once delivery without distributed transactions.

Key Interview Q&A

Q: How do you handle distributed transactions across microservices?
Avoid 2PC (two-phase commit) — it is slow and brittle. Use the Saga pattern instead. For choreography, each service publishes an event on success and listens for compensating events on failure. For orchestration, a saga orchestrator coordinates steps and triggers compensations. Combine with the Outbox Pattern for reliable event publishing.
Q: When would you NOT use microservices?
Small teams, early-stage products, when domain boundaries are unclear, or when the operational cost (monitoring, tracing, deployment pipelines per service) outweighs the benefit. Start with a well-modularized monolith and extract services when you have clear bounded contexts and scaling needs.

Event-driven architecture decouples producers from consumers via events. CQRS and Event Sourcing are complementary patterns for systems with complex domain logic or asymmetric read/write loads.

Core Concepts

  • Event vs Command vs Query: An Event is a fact that happened (past tense, immutable: OrderPlaced). A Command is a request to do something (imperative: PlaceOrder). A Query is a request for data (no side effects: GetOrderStatus).
  • Event Sourcing: Store state as a sequence of events (append-only log) instead of current state. Rebuild current state by replaying events. Use snapshots every N events to speed up replay. Pros: full audit trail, time-travel debugging, enables CQRS. Cons: complexity, schema evolution, eventual consistency.
  • CQRS: Separate read models (optimized for queries, possibly denormalized) from write models (handle commands, enforce business rules). Read and write models can use different databases. Sync via events.
  • Idempotency: Operations that produce the same result when applied multiple times. Techniques: idempotency keys (client-generated UUID stored server-side), natural idempotency (PUT replaces entire resource), upsert (INSERT ON CONFLICT DO UPDATE).
  • Outbox Pattern: Write the event to a local DB table within the same transaction. A relay process (CDC or polling) publishes it to the broker. Ensures exactly-once semantics at the boundary.

Key Interview Q&A

Q: What problems does Event Sourcing solve that a traditional DB doesn't?
Full audit trail (every state change recorded), temporal queries (state at any point in time), easy event-driven integration (events are the source of truth), and debugging (replay to reproduce bugs). The trade-off is increased complexity in querying current state, handling schema evolution, and managing storage growth.
Q: Do you always need CQRS with Event Sourcing?
No, but they pair well. Event Sourcing makes writes an event log, which is poor for queries. CQRS adds optimized read models projected from events. You can use CQRS without Event Sourcing (e.g., separate read replicas) or Event Sourcing without CQRS (query the event stream directly, though this is slow).

REST is the most widely used API style. Understanding its constraints, proper use of HTTP semantics, and real-world design patterns is fundamental for any backend engineer.

Core Concepts

  • Fielding's Constraints: Client-server, stateless, cacheable, uniform interface (resource identification via URI, manipulation through representations, self-descriptive messages, HATEOAS), layered system, code-on-demand (optional).
  • HTTP Methods & Idempotency:
MethodSafeIdempotentUse
GETYesYesRead a resource
POSTNoNoCreate / trigger action
PUTNoYesFull replace
PATCHNoNo*Partial update
DELETENoYesRemove a resource
  • Status Codes: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Entity, 429 Too Many Requests, 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable.
  • Versioning: URI path (/v1/users) — most common. Header (Accept: application/vnd.api+json;version=2). Query param (?version=2). URI path is simplest to reason about.
  • Pagination: Offset: simple but slow for large offsets (DB scans). Cursor: opaque token, consistent for real-time data. Keyset: WHERE id > last_seen ORDER BY id LIMIT N, performant and stable.

Key Interview Q&A

Q: Why is offset pagination problematic at scale?
The database must scan and discard OFFSET rows before returning results. At offset 1,000,000 with limit 20, it processes 1,000,020 rows. Keyset/cursor pagination uses an indexed WHERE clause, making every page equally fast regardless of depth.
Q: PATCH is listed as non-idempotent. Why?
A JSON Merge Patch (replace fields) is idempotent in practice. But the PATCH spec allows non-idempotent operations (e.g., {"op":"add","path":"/tags/-","value":"new"} in JSON Patch appends, so applying it twice adds the tag twice). The HTTP spec does not guarantee idempotency.

GraphQL provides a typed schema and lets clients request exactly the data they need. It solves over-fetching and under-fetching but introduces its own challenges around performance and security.

Core Concepts

  • Schema-First: Define types, queries, mutations, and subscriptions in SDL. The schema is the contract. Code-first alternatives (e.g., Strawberry, TypeGraphQL) generate SDL from code.
  • Resolver Chain: Each field has a resolver. Parent resolver result is passed down. Resolvers compose in a tree: Query.user → User.posts → Post.comments.
  • N+1 Problem & DataLoader: Naive resolvers: 1 query for user, N queries for each user's posts. DataLoader batches and caches: collects all requested IDs within one event loop tick, issues one batch query. DataLoader instances must be per-request (not global) to avoid stale cache.
  • When GraphQL vs REST: GraphQL excels for: varied client needs (mobile vs web), deeply nested data, rapid iteration. REST is better for: simple CRUD, caching (HTTP cache works naturally), file uploads, public APIs.
  • Security: Depth limiting: reject queries deeper than N levels. Complexity analysis: assign cost to each field, reject queries above threshold. Disable introspection in production. Field-level authorization in resolvers (not just endpoint-level).

Key Interview Q&A

Q: How does DataLoader solve the N+1 problem?
DataLoader collects all load calls made during the same tick of the event loop into a batch. Instead of N individual queries, it issues one query with all IDs (e.g., SELECT * FROM posts WHERE user_id IN (...)). Results are cached for the request duration to prevent duplicate fetches.
Q: How do you prevent a malicious deeply nested query from DoS-ing your server?
Three layers: (1) Depth limiting — reject queries deeper than a threshold (e.g., 10 levels). (2) Complexity analysis — assign costs to fields and reject queries exceeding a budget. (3) Rate limiting per client. Also disable introspection in production.

Serverless lets you run code without managing servers. AWS Lambda is the most common. Understanding when to use it and the anti-patterns to avoid is critical.

Core Concepts

  • When to Use: Event-driven workloads, variable traffic with idle periods, quick prototypes, glue logic between services, scheduled tasks. Not ideal for: long-running processes, stateful workloads, consistent low-latency requirements, heavy compute.
  • Lambda + DynamoDB Cart Abandonment: S3 event → Lambda processes upload → writes to DynamoDB with TTL. DynamoDB Streams → Lambda detects TTL expiry → sends cart reminder via SES/SNS. Fully serverless, scales to zero.
  • Anti-Patterns: Lambda-lith: cramming an entire Express/Flask app into one Lambda (defeats purpose, cold start penalty). Synchronous chains: Lambda A calls Lambda B calls Lambda C (latency compounds, use Step Functions). Ignoring cold starts: not using provisioned concurrency for latency-sensitive paths.

Key Interview Q&A

Q: How do you reduce Lambda cold start times?
Provisioned concurrency (keeps instances warm), smaller deployment packages, use lightweight runtimes (Node.js/Python over Java), lazy-load SDK clients, SnapStart (Java), keep functions focused (not a monolith).

Deploying schema changes and code updates without downtime requires careful sequencing. The Expand-Contract pattern and safe PostgreSQL operations are essential knowledge.

Core Concepts

  • Expand-Contract Pattern (3 steps): (1) Expand: add new column/table, deploy code that writes to both old and new. (2) Migrate: backfill existing data, switch reads to new. (3) Contract: remove old column/table and old code paths.
  • Dangerous PostgreSQL Operations: ADD COLUMN DEFAULT (pre-PG11 rewrites table — PG11+ is safe). CREATE INDEX locks writes — use CREATE INDEX CONCURRENTLY. Adding NOT NULL constraint scans entire table — add as CHECK constraint with NOT VALID, then VALIDATE separately.
  • Deployment Strategies: Rolling: replace instances one by one (requires backward compatibility). Blue-Green: two identical environments, switch traffic at once (instant rollback). Canary: route small percentage to new version, monitor, gradually increase. Feature Flags: decouple deployment from release (deploy dark, enable for users gradually).

Key Interview Q&A

Q: How do you rename a database column with zero downtime?
Never rename directly. (1) Add new column, (2) deploy code to write both, (3) backfill old rows, (4) deploy code to read from new, (5) stop writing to old, (6) drop old column. Each step is a separate deployment.

Autoscaling dynamically adjusts compute resources based on demand. Getting the strategy right means balancing cost, performance, and availability.

Core Concepts

  • Horizontal vs Vertical: Horizontal adds more instances (preferred for stateless services). Vertical increases instance size (limited ceiling, requires restart).
  • HPA Custom Metrics: Scale on application-specific metrics (queue depth, request latency, active connections) via Prometheus adapter or custom metrics API. Better than CPU-only scaling for event-driven workloads.
  • KEDA (scale-to-zero): Kubernetes Event-Driven Autoscaler. Scales deployments from 0 based on event sources (Kafka lag, SQS queue length, cron). Saves cost during idle periods.
  • Aggressive Up / Conservative Down: Scale up quickly (seconds) to handle traffic spikes. Scale down slowly (minutes) to avoid flapping. Use stabilization windows and cooldown periods.
  • Pod Disruption Budgets (PDB): Guarantee minimum available pods during voluntary disruptions (node drain, cluster upgrade). minAvailable or maxUnavailable.
  • Load Testing: Use k6, Locust, or Artillery. Measure p50, p95, p99 latencies. Find the breaking point. Test autoscaling behavior under ramp-up.

Key Interview Q&A

Q: Why is CPU-based autoscaling insufficient for queue-processing workloads?
Queue processors may have low CPU usage but high backlog. The metric that matters is queue depth (messages waiting). KEDA can scale based on SQS ApproximateNumberOfMessages or Kafka consumer lag, spinning up workers when the queue grows and scaling to zero when it drains.

Cloud costs can spiral without discipline. Cost optimization is an ongoing practice that balances performance with spend.

Core Concepts

  • Compute: Right-size instances (monitor actual CPU/memory use). Use spot/preemptible instances for fault-tolerant workloads (60-90% cheaper). Reserved instances / savings plans for steady-state. Scale-to-zero for dev/staging environments.
  • Storage: Lifecycle policies (S3 Intelligent-Tiering, move to Glacier after N days). Compression (gzip, zstd) for logs and backups. Right-size EBS volumes (gp3 over gp2, provision only needed IOPS).
  • Database: Connection pooling (PgBouncer) to reduce idle connections. Read replicas for read-heavy workloads. Caching (Redis) to reduce DB queries. DynamoDB on-demand vs provisioned (model the break-even).

Key Interview Q&A

Q: How would you reduce cloud costs by 30% without impacting performance?
Audit for: (1) idle resources (dev instances running 24/7 — schedule or scale to zero), (2) over-provisioned instances (right-size based on actual metrics), (3) spot instances for batch/CI, (4) reserved instances for production base load, (5) caching to reduce DB and API calls, (6) storage tiering for old data.

System design interviews test your ability to architect scalable systems under ambiguity. Having a structured framework ensures you cover all bases in 45 minutes.

5-Step Framework

  • 1. Requirements (3-5 min): Functional requirements (what does the system do), non-functional (scale, latency, availability, consistency), clarify scope (what is NOT in scope).
  • 2. High-Level Design (5-10 min): Draw main components (clients, load balancer, application servers, databases, caches, queues). Define data flow for core operations.
  • 3. Data Model & API (5 min): Define key entities, relationships, database choice (SQL vs NoSQL). Define API endpoints with HTTP methods.
  • 4. Deep Dive (15-20 min): Discuss 2-3 areas in depth (scaling bottlenecks, trade-offs, failure scenarios). This is where you differentiate yourself.
  • 5. Wrap-Up (2-3 min): Summarize trade-offs made, mention what you would add with more time (monitoring, security, analytics).

Key Interview Q&A

Q: Design a URL Shortener — what are the key decisions?
Key decisions: (1) ID generation — hash (MD5/SHA, take first 7 chars) vs counter (base62 encode). (2) Storage — key-value store (DynamoDB) for high throughput. (3) Redirection — 301 (cacheable) vs 302 (trackable). (4) Analytics — async logging via Kafka. (5) Scale — read-heavy, cache popular URLs in Redis.
Q: Back-of-envelope: How much storage for 1 billion URLs?
Each URL record: ~500 bytes (short URL + long URL + metadata). 1B x 500B = 500 GB. Fits on a single modern SSD. With replication factor 3: ~1.5 TB. Storage is not the bottleneck; read throughput is.

Cloud Platforms

AWS is the dominant cloud provider. Lambda, DynamoDB, Fargate, and messaging services (SQS/SNS/EventBridge) form the backbone of modern serverless and container-based architectures.

Lambda

  • Cold Start: First invocation initializes runtime, loads code. Duration: ~100ms (Python/Node), ~1-3s (Java). Warm Start: reuses existing container. Provisioned Concurrency: pre-warms N instances (eliminates cold starts, costs more).
  • Memory/CPU Scaling: CPU scales linearly with memory (at 1769 MB you get 1 full vCPU). More memory = faster execution = potentially lower cost.
  • 15 min timeout: Hard limit. For longer tasks, use Step Functions, Fargate, or break into smaller Lambdas.
  • Common Patterns: API Gateway + Lambda (REST APIs), SQS + Lambda (async processing), S3 + Lambda (file processing), DynamoDB Streams + Lambda (change data capture).

DynamoDB

  • PK/SK: Partition Key determines data distribution. Sort Key enables range queries within a partition. Design access patterns first, then model the table.
  • Single Table Design: Store multiple entity types in one table using PK/SK overloading. Reduces costs and latency (one query gets related data). Trade-off: complex, hard to evolve.
  • On-Demand vs Provisioned: On-demand: pay per request (good for unpredictable traffic). Provisioned: set RCU/WCU (cheaper for steady traffic, use autoscaling).
  • Consistency: Eventually consistent reads (default, half the cost). Strongly consistent reads (latest data, from leader node, double cost).
  • GSI vs LSI: GSI: alternate PK+SK, own throughput, eventually consistent. LSI: same PK, different SK, must be created at table creation, strongly consistent reads possible.

Fargate & Messaging

  • Fargate: Serverless containers (no EC2 management). vs Lambda: Fargate for long-running tasks, larger packages, persistent connections. vs ECS on EC2: Fargate is simpler but costlier; EC2 gives control over instance types, GPU, spot.
  • SQS vs SNS vs EventBridge: SQS: point-to-point queue (decoupling, buffering). SNS: pub/sub fan-out (one message to many subscribers). EventBridge: event bus with routing rules, schema registry, 30+ AWS service integrations, content-based filtering.

Key Interview Q&A

Q: How do you handle DynamoDB hot partitions?
Causes: one partition key gets disproportionate traffic. Solutions: (1) add randomness to PK (write sharding with suffix 0-N), (2) use a more granular PK, (3) DynamoDB adaptive capacity redistributes throughput automatically, (4) DAX (in-memory cache) absorbs reads.

Google Cloud Platform offers GKE (managed Kubernetes) and Cloud Run (serverless containers) as primary compute options for backend services.

Core Concepts

  • GKE Standard vs Autopilot: Standard: you manage node pools, sizing, autoscaling. Autopilot: Google manages nodes, you only define pods (pay per pod resources). Autopilot simplifies ops but limits customization (no DaemonSets, SSH, privileged containers).
  • HPA + Custom Metrics: HPA scales pods based on CPU/memory or custom metrics from Cloud Monitoring / Prometheus. Use Stackdriver adapter for custom metric scaling.
  • KEDA for Scale-to-Zero: KEDA extends HPA to support scale-to-zero. Useful for Pub/Sub consumers, batch processors that should not run when idle.
  • GPU Scheduling: Use node pools with GPU accelerators (NVIDIA T4, A100). Set nvidia.com/gpu resource requests. Node auto-provisioning can add GPU nodes on demand.
  • Preemptible VMs / Spot VMs: Up to 80% cheaper, but can be terminated with 30s notice. Use for batch processing, CI/CD, stateless workloads with retry logic.
  • Cloud Run: Serverless containers that scale from zero to thousands. Cold start: ~1-2s. Supports WebSockets, gRPC, concurrent requests per instance (up to 1000). vs GKE: Cloud Run for simpler stateless services; GKE for complex orchestration, stateful workloads, fine-grained control.

Key Interview Q&A

Q: When would you choose Cloud Run over GKE?
Cloud Run: stateless HTTP/gRPC services, event-driven processing, teams without Kubernetes expertise, when you want zero-ops scaling. GKE: need service mesh, StatefulSets, complex networking policies, GPU workloads, long-running background processes, or multi-container pods.

Key Interview Q&A

Q: How would you design a hybrid content moderation system?
Tier 1: Azure Content Moderator API for immediate, automated screening (text, image). Tier 2: custom ML model for domain-specific content. Tier 3: human review queue for edge cases (confidence below threshold). Include feedback loop: human decisions retrain the custom model. Track false positive/negative rates to tune thresholds.

DevOps & Infrastructure

Kubernetes is the de-facto container orchestration platform. Understanding its architecture, core objects, networking, and autoscaling is essential for backend roles.

Architecture

  • Control Plane: kube-apiserver (REST gateway), etcd (distributed KV store for cluster state), kube-scheduler (assigns pods to nodes), kube-controller-manager (runs controllers: ReplicaSet, Deployment, etc.).
  • Worker Nodes: kubelet (ensures containers are running), kube-proxy (network rules, service routing), container runtime (containerd, CRI-O).

Core Objects

  • Pod: Smallest deployable unit. One or more containers sharing network namespace and storage volumes.
  • Deployment: Manages ReplicaSets for stateless apps. Handles rolling updates, rollbacks, scaling.
  • Service Types: ClusterIP (internal), NodePort (expose on node port), LoadBalancer (cloud LB), ExternalName (DNS alias).
  • ConfigMap/Secret: Decouple config from images. Secrets are base64-encoded (not encrypted at rest by default — enable EncryptionConfiguration or use external secrets).
  • StatefulSet: Ordered, stable pod identities and persistent storage. Use for databases, Kafka, ZooKeeper.
  • DaemonSet: One pod per node (log collectors, monitoring agents, node-level services).
  • Job/CronJob: Run-to-completion tasks. CronJob for scheduled batch processing.

Networking & Autoscaling

  • CNI: Container Network Interface plugin (Calico, Cilium, Flannel). Every pod gets a unique IP.
  • Ingress: HTTP/HTTPS routing to services. TLS termination, path-based routing, virtual hosts.

Docker containerizes applications for consistent environments across dev, staging, and production. Writing efficient, secure Dockerfiles is a core backend skill.

Core Concepts

  • Multi-Stage Builds: Use multiple FROM statements. Build stage compiles/installs dependencies; final stage copies only the artifact. Drastically reduces image size.
# Build stage
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

# Production stage
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
USER node
CMD ["node", "dist/index.js"]
  • Layer Caching: Each instruction creates a layer. Order instructions from least-to-most frequently changing. Copy package.json and install dependencies before copying source code.
  • .dockerignore: Exclude node_modules, .git, *.md, test files from the build context. Speeds up builds and reduces image size.
  • Security: Use non-root user (USER node). Use minimal base images (alpine, distroless). Never put secrets in images (use build args or secret mounts). Scan images with Trivy/Snyk.
  • Networking: bridge (default, isolated network per host), host (share host network, better performance, no isolation), none (no networking).

Key Interview Q&A

Q: Why should you copy package.json before the source code?
Docker caches layers. If source code changes but package.json does not, the npm ci layer is cached and not re-executed. If you copy everything first, any source change invalidates the dependency install layer, making builds much slower.
Q: What is the difference between CMD and ENTRYPOINT?
ENTRYPOINT defines the executable; CMD provides default arguments. docker run myimage --flag replaces CMD but appends to ENTRYPOINT. Use ENTRYPOINT for the main process and CMD for default flags. Both can be overridden at runtime.

Databases

MongoDB is a document database (BSON/JSON). Schema design decisions (embedding vs. referencing) and proper indexing are critical for performance.

Core Concepts

  • Schema Design — Embed vs Reference: Embed when data is accessed together, has a 1:few relationship, and is bounded. Reference when data is shared across documents, has a many:many relationship, or is unbounded.
  • Unbounded Array Anti-Pattern: Arrays that grow indefinitely (e.g., all comments on a post) cause document growth, working set bloat, and eventually hit the 16MB document limit. Solution: use a separate collection with a foreign key.
  • Indexing: Single field: most common. Compound (ESR rule): Equality fields first, Sort fields next, Range fields last. Multikey: automatic for array fields. Text: full-text search. Partial: index a subset of documents (sparse). TTL: auto-delete documents after time.
  • Aggregation Pipeline: $match (filter early), $group (aggregate), $sort, $lookup (left outer join), $unwind (flatten arrays), $facet (multiple aggregations in parallel). Place $match first to use indexes.
  • Replication: Replica set: primary + secondaries. Automatic failover. Read preference: primary (default), secondary (for reads), nearest.
  • Sharding: Horizontal partitioning. Shard key selection is critical and immutable. Hashed shard key: even distribution. Ranged shard key: range queries efficient. Avoid monotonically increasing shard keys (hot partition).

Key Interview Q&A

Q: What is the ESR rule for compound indexes?
Equality, Sort, Range. Place fields used in equality matches first (exact match narrows candidates), then sort fields (avoids in-memory sort), then range fields last. Example: for find({status: "active", age: {$gte: 25}}).sort({name: 1}), create index {status: 1, name: 1, age: 1}.

PostgreSQL is the most advanced open-source relational database. Deep knowledge of MVCC, indexing strategies, and query optimization is expected in backend interviews.

Core Concepts

  • MVCC: Multi-Version Concurrency Control. Each row version has xmin (creating transaction) and xmax (deleting/updating transaction). Readers never block writers. Dead tuples accumulate and must be cleaned by VACUUM. autovacuum runs automatically but may need tuning for high-write tables.
  • Index Types: B-tree: default, equality and range queries. GIN: Generalized Inverted Index (arrays, JSONB, full-text search). GiST: geometric, full-text, range types. BRIN: Block Range Index (huge tables with naturally ordered data, very small). Hash: equality only (rarely used, B-tree is almost always better). Partial: WHERE clause on index (index active users only). Expression: index on function result (CREATE INDEX ON users (lower(email))). Covering/INCLUDE: add non-key columns for index-only scans.
  • EXPLAIN ANALYZE: Shows actual execution plan with timings. Key nodes: Seq Scan (full table scan), Index Scan (traverse index + heap lookup), Index Only Scan (no heap, if visibility map is fresh), Bitmap Index Scan (for medium selectivity). Join types: Nested Loop (small inner), Hash Join (equality, medium tables), Merge Join (both sorted). work_mem affects sort and hash operations.
  • Partitioning: Range: by date (most common). List: by category. Hash: even distribution. Partition pruning: query planner skips irrelevant partitions when the partition key is in the WHERE clause.
  • Connection Pooling (PgBouncer): PostgreSQL forks a process per connection (expensive). PgBouncer multiplexes connections. Modes: session (one server conn per client session), transaction (release after each transaction — most efficient), statement (per statement, limited use).

Key Interview Q&A

Q: Why would VACUUM not keep up, and what happens?
Causes: very high write rate, long-running transactions holding back the visibility horizon, autovacuum too conservative (not enough workers, too high thresholds). Consequences: table bloat (dead tuples consume disk), index bloat, and eventually transaction ID wraparound (database shuts down to prevent data corruption). Fix: tune autovacuum settings per table, kill long transactions, run manual VACUUM on critical tables.
Q: When would you use a BRIN index?
For very large tables (100M+ rows) where data is physically ordered by the indexed column (e.g., timestamp in append-only tables, auto-incrementing IDs). BRIN stores min/max per block range — tiny index size (1000x smaller than B-tree) but only useful when correlation between physical storage order and column value is high.

Redis is an in-memory data structure store used as a cache, database, and message broker. Its rich data structures go far beyond simple key-value caching.

Core Concepts

  • Data Structures: Strings: basic KV, counters (INCR). Hashes: field-value maps (user profiles). Lists: ordered collections (queues, feeds). Sets: unique elements (tags, online users). Sorted Sets: scored elements (leaderboards, rate limiting). Streams: append-only log (event streaming). HyperLogLog: probabilistic cardinality counting (unique visitors with 0.81% error using 12KB).
  • Caching Patterns: Cache-Aside: app checks cache; on miss, reads DB, writes to cache. Most common. Write-Through: write to cache and DB simultaneously. Write-Behind: write to cache, async batch write to DB (higher throughput, risk of data loss).
  • Cache Stampede: When a popular key expires, many concurrent requests hit the DB. Solutions: Locking: only one request fetches, others wait. Probabilistic early recomputation: refresh before TTL expires. Stale-while-revalidate: serve stale data while refreshing in background.
  • Persistence: RDB: point-in-time snapshots (compact, slow recovery). AOF: append-only file logging every write (durable, slower, larger). Hybrid (RDB+AOF): best of both (recommended for production).
  • Clustering: Redis Cluster: data sharding across nodes (16384 hash slots), automatic failover, horizontal scaling. Sentinel: HA for single-instance Redis (monitors, notification, automatic failover, no sharding).

Key Interview Q&A

Q: How would you implement a rate limiter with Redis?
Sliding window with Sorted Sets: for each request, add timestamp as score. ZRANGEBYSCORE to count requests in the window. ZREMRANGEBYSCORE to clean old entries. Atomic with Lua script. Alternatively, use the simpler fixed window with INCR + EXPIRE (less precise but simpler).
Q: Redis Cluster vs Sentinel — when to use which?
Sentinel: HA for a single dataset that fits in one node's memory. Provides automatic failover and monitoring. Cluster: when data exceeds one node's memory and you need horizontal scaling (sharding). Cluster also provides HA. Start with Sentinel, migrate to Cluster when you outgrow one node.

Kafka is a distributed event streaming platform for high-throughput, fault-tolerant, real-time data pipelines. It is the backbone of event-driven architectures.

Core Concepts

  • Architecture: Broker: a Kafka server. Topic: a named stream of records. Partition: ordered, immutable sequence of records within a topic (unit of parallelism). Offset: sequential ID for each record in a partition. Consumer Group: each partition assigned to one consumer in the group (enables parallel consumption). Replication: each partition replicated across brokers (leader + followers, ISR).
  • Delivery Semantics: At-most-once: commit offset before processing (may lose messages). At-least-once: commit after processing (may duplicate). Exactly-once (EOS): transactional producer + idempotent consumer (Kafka Streams transactions, or consumer idempotency).
  • Schema Evolution: Use Avro + Schema Registry for schema enforcement and backward/forward compatibility. Schema Registry ensures producers and consumers agree on format.
  • Error Handling: DLQ (Dead Letter Queue): route failed messages to a separate topic for manual inspection. Retry topic: auto-retry with backoff before DLQ.
  • Ordering: Guaranteed within a partition. Use message key to route related messages to the same partition (e.g., user_id as key ensures all events for a user are ordered).
  • Kafka Connect & Debezium CDC: Kafka Connect: framework for connecting Kafka to external systems (DB, S3, Elasticsearch). Debezium: CDC connectors that capture database changes (inserts/updates/deletes) as Kafka events in real-time.
  • Consumer Lag: Difference between latest offset and consumer's committed offset. High lag means consumer is falling behind. Monitor with Burrow, Kafka Lag Exporter, or built-in consumer group commands.

Key Interview Q&A

Q: How does Kafka achieve exactly-once semantics?
Two components: (1) Idempotent producer: assigns sequence numbers to messages, broker deduplicates retries. (2) Transactions: producer atomically writes to multiple partitions and commits offsets. For end-to-end EOS in Kafka Streams, enable processing.guarantee=exactly_once_v2. For external systems, the consumer must be idempotent (use a deduplication table or idempotent writes).

ElasticSearch is a distributed search and analytics engine built on Apache Lucene. It excels at full-text search, log analytics, and real-time data exploration.

Core Concepts

  • Inverted Index: Maps each term to the list of documents containing it (like a book index). Enables fast full-text search. Each field can have its own inverted index.
  • Analyzer: Tokenizer (splits text into terms) + token filters (lowercase, stemming, synonyms, stop words). Standard analyzer: lowercase + word tokenizer. Custom analyzers for domain-specific needs.
  • Mappings: Dynamic: ES auto-detects types (convenient, sometimes wrong). Explicit: define types manually. keyword: exact match, aggregation, sorting (not analyzed). text: full-text search (analyzed, tokenized).
  • Query DSL: Query context: "how well does this match?" (scoring). Filter context: "does this match? yes/no" (cacheable, no scoring). match: full-text. term: exact value. bool: combine with must/should/must_not/filter. range: numeric/date ranges.
  • Performance: Shard sizing: 10-50GB per shard. Too many small shards: overhead. Too few large shards: slow queries. Refresh interval: how often new docs become searchable (default 1s, increase for write-heavy). Deep pagination: from+size is O(from+size) on each shard; use search_after for efficient deep pagination or scroll for batch exports.

Key Interview Q&A

Q: Why is the keyword type different from the text type?
text fields are analyzed (tokenized, lowercased, stemmed) for full-text search — you cannot sort or aggregate on them efficiently. keyword fields are indexed as-is for exact matches, sorting, and aggregations. Common pattern: map a field as both (multi-field) with title as text and title.keyword as keyword.

Qdrant is a vector similarity search engine for AI applications. It stores high-dimensional vectors with payloads and enables fast approximate nearest neighbor (ANN) search.

Core Concepts

  • Collection: A named group of points with a defined vector size and distance metric.
  • Point: A vector (embedding) + optional payload (metadata as JSON). The vector is the searchable content; the payload enables filtering.
  • Distance Metrics: Cosine: angle between vectors (most common for text embeddings, direction-only). Dot Product: considers magnitude (useful when vector length is meaningful). Euclidean: straight-line distance (good for spatial data).
  • HNSW Index: Hierarchical Navigable Small World graph. Builds a multi-layer graph for efficient ANN search. Configurable: m (connections per node, higher = more accurate, more memory), ef_construct (build-time search width).
  • Filtered Vector Search: Pre-filtering: apply payload filter first, then search vectors in filtered subset (exact but may be slow if filter is very selective). Post-filtering: search vectors first, then filter results (fast but may return fewer results than requested). Qdrant uses smart hybrid approach.
  • Payload Indexing: Create indexes on payload fields for fast filtering. Keyword index for exact match, integer/float index for range queries.
  • Vector Search vs Full-Text: Vector search finds semantically similar content (captures meaning). Full-text search finds lexically matching content (exact terms). Best practice: hybrid search combining both (e.g., BM25 for candidates, vector reranking).

Key Interview Q&A

Q: When would you use vector search instead of full-text search?
Vector search excels at semantic similarity (find documents about "automobile" when searching "car"), multilingual matching, image/audio similarity, and recommendation. Full-text search is better for exact keyword matching, boolean queries, and when users know the exact terms. Many production systems use hybrid: BM25 for candidate retrieval, vector similarity for reranking.

DuckDB is an in-process OLAP database (the "SQLite of analytics"). It runs inside your application process with zero external dependencies and excels at analytical queries on local data.

Core Concepts

Q: Why is DuckDB faster than PostgreSQL for analytics?

(3) No client-server overhead — runs in-process, no network round trips. For a 100M-row aggregation, DuckDB can be 100x faster.

LangGraph is a framework for building stateful, multi-step AI agent workflows as directed graphs. Understanding its state management and persistence model is key for production agentic systems.

Core Concepts

  • StateGraph: Define a TypedDict (or Pydantic model) for state. Add nodes (functions that take state, return partial state updates). Add edges (transitions between nodes). Conditional edges route based on state values (if/else logic in the graph).
  • Checkpointing & Persistence: Save graph state at each step. MemorySaver for development (in-memory). PostgresSaver / SqliteSaver for production. Enables: resume after failure, time-travel debugging, human-in-the-loop interrupts.
  • Resume After Failure: If a node fails (API error, timeout), the graph state is checkpointed at the last successful node. On retry, execution resumes from the failure point, not from scratch.
  • Subgraphs: Compose graphs hierarchically. A node in one graph can be another complete graph. Enables modular agent design (research subgraph, writing subgraph, review subgraph).
  • FactGet Architecture: Specialized agents (claim analyzer, source validator, evidence ranker) as nodes. Parallel claim analysis using map-reduce pattern. Memory compression for long-running conversations. Token/cost tracking per node for budget management.

Key Interview Q&A

Q: Why use LangGraph instead of a simple chain?
Chains are linear (A → B → C). LangGraph supports: (1) Cycles — agent loops (think, act, observe, repeat). (2) Conditional routing — different paths based on results. (3) Persistence — pause, resume, human approval. (4) Parallel execution — fan-out to multiple nodes. Use chains for simple pipelines; LangGraph for stateful, branching, or looping workflows.

Entity resolution (record linkage / deduplication) determines which records across datasets refer to the same real-world entity. Critical for data quality, compliance, and sanctions screening.

Core Concepts

  • Record Linkage Problem: Given records from multiple sources without a shared unique ID, find which records refer to the same entity. Challenges: name variations, typos, missing fields, different formats.
  • Splink: Open-source Python library for probabilistic record linkage. Blocking: reduce comparison space (instead of N x M, compare only records that share a blocking key like first letter of name + birth year). Comparison Levels: for each field, define levels of similarity (exact match, fuzzy match, partial match) with associated match weights. EM Training: Expectation-Maximization algorithm estimates match/non-match probabilities without labeled training data. Match Probability: Fellegi-Sunter model produces a probability that two records are the same entity.
  • Sanctions Screening: Match customer records against sanctions lists (OFAC, EU, UN). Challenges: multilingual name matching (transliteration), exact identifier matching (passport, DOB), high recall requirement (must not miss true matches). Use BM25 for candidate retrieval, then Splink for detailed comparison.
  • BM25 Formula: Best Matching 25, a ranking function for information retrieval. TF: term frequency in the document (saturates with k1 parameter). IDF: inverse document frequency (rarer terms score higher). Length normalization: controlled by parameter b (0 = no normalization, 1 = full normalization). Parameters: k1 (typically 1.2-2.0, controls TF saturation), b (typically 0.75, controls length normalization).
  • BM25 vs Vector Search: BM25: exact lexical matching, no training needed, interpretable scores, great for names and identifiers. Vector search: semantic similarity, handles synonyms, needs embeddings. For entity resolution: BM25 is often better for name matching; combine both for robust candidate retrieval.
  • Operational Patterns: Idempotent ingestion (re-processing same list should not create duplicates). Source freshness tracking (detect stale sanctions lists). Delisting safety gates (require explicit confirmation before removing a match). Audit trail (every match decision logged with rationale).

Key Interview Q&A

Q: Why use blocking in entity resolution instead of comparing all pairs?
Without blocking, comparing N records requires N*(N-1)/2 comparisons. For 1M records, that is ~500 billion comparisons — computationally infeasible. Blocking partitions records into groups that share a blocking key (e.g., first 3 letters of surname + birth year). Only records within the same block are compared. This reduces comparisons by 99%+ while missing very few true matches (if blocking keys are well-chosen).
Q: Explain BM25's k1 and b parameters.
k1 controls term frequency saturation. Low k1 (0.5): even one occurrence scores high. High k1 (2.0): more occurrences continue to increase score. b controls document length normalization. b=0: no length normalization (long and short documents treated equally). b=1: fully normalize (long documents penalized). Typical values: k1=1.2, b=0.75.
